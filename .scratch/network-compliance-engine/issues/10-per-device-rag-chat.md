# 10: Per-device RAG chat

**What to build:** A chat interface scoped to a single device's report, grounded via a local vector store over that device's facts/findings/remediation and the relevant control text across all four frameworks, with self-verified, cited answers.

**Blocked by:** 04

**Status:** done

- [x] Each device's normalized facts, findings, remediation text, and the relevant control text (across all four frameworks) are embedded into a local, file-based vector store using a local embedding model.
- [x] The admin can ask natural-language questions about that device's report and receive answers retrieved from that device's index, not from unrelated devices.
- [x] Answers cite the specific finding/control they're grounded in.
- [x] Each answer goes through the same interpret-then-verify two-pass pattern used elsewhere before being shown.
- [x] The vector index and chat history persist to disk per device and survive an app restart.
- [x] No secret-shaped values are ever embedded or surfaced in chat, consistent with the redaction applied at normalization.

## Comments

**`LlmClient` interface (`backend/app/llm.py`)** -- a `typing.Protocol` with exactly three methods: `interpret(prompt: str) -> str`, `verify(claim: str, context: str) -> bool`, `embed(text: str) -> list[float]`. No separate `chat` method: for this ticket, `interpret` called with a prompt built from the question plus retrieved context *is* chat-answer generation, so a fourth/fifth concept wasn't earning its keep (per the codebase's stated minimal-indirection preference). Two implementations:
- `OllamaLlmClient` -- real implementation over `httpx`, calling Ollama's `/api/generate` (used for both `interpret` and `verify`, via different prompts -- one model, two roles via prompting, per the spec's AI pipeline decision) and `/api/embeddings`. `__init__` parses `base_url` and raises `ValueError` unless the host is `localhost`/`127.0.0.1` -- this is the only thing in the whole ticket that makes a network call, and it structurally cannot talk to anything but localhost.
- `FakeLlmClient` -- deterministic, in-memory. `interpret_response`/`verify_result` are plain settable constructor args/attributes so a test can reprogram them mid-test. `embed` is a SHA-256-hash-based fixed-length (32-dim) vector -- not semantically meaningful, but deterministic and stable per input text, so retrieval in tests is reproducible without a real embedding model.

**Vector store (`backend/app/vectorstore.py`)** -- a `DeviceVectorStore` wrapping a persistent `chromadb.PersistentClient` rooted at `data_dir / "vectorstore"`, with **one Chroma collection per device** (named `device_<device_id>`), not one shared collection filtered by a `device_id` metadata field. This was a deliberate judgment call: with per-device collections, cross-device leakage is structurally impossible (there's no filter to get wrong, and a query against device A's collection object literally cannot return device B's rows), rather than merely being prevented by correct filter code. Indexing is lazy (`ensure_indexed`, triggered on every chat request, no-op once `collection.count() > 0`) and produces one chunk per CIS/NIST/STIG finding plus one chunk per ISO Annex A fact-evidence entry, each embedded via `LlmClient.embed()` and tagged with metadata (`control_id`, `framework`, `title`, `status`) for citation. One nuance surfaced by real fixture data: NIST/STIG map several facts to the same `control_id` (many-to-one, unlike CIS's 1:1), so a naive `framework:control_id` chunk id collided (`DuplicateIDError`) -- fixed by appending the finding's list index to the id.

**Chat history (`backend/app/chat_store.py`)** -- a small `ChatHistoryStore`, deliberately *not* reusing `storage.DeviceStore`: `DeviceStore.save()` always mints a fresh uuid per call, which doesn't fit chat history's "one growing list keyed by an already-known device_id, upserted on every exchange" shape. `ChatHistoryStore` mirrors `DeviceStore`'s JSON-payload-encrypted-with-Fernet-over-sqlite pattern exactly, just keyed by `device_id` with an `INSERT ... ON CONFLICT DO UPDATE` upsert. This was the only way to avoid touching `storage.py` (a shared file) while still following its established encryption-at-rest discipline.

**Chat router (`backend/app/chat.py`)** -- `POST /api/devices/{device_id}/chat` (body: `{"question": str}`) and `GET /api/devices/{device_id}/chat`, both session-gated via `Depends(require_session)` and 404-on-missing-device, matching `devices.py`'s conventions exactly (it even reuses the same `DeviceRecordCorrupted` -> 500 handling). Flow: load device record -> `vector_store.ensure_indexed` -> retrieve top-4 chunks from that device's collection -> `llm_client.interpret(question + context)` for a draft answer -> `llm_client.verify(draft, context)` as the adversarial second pass -> only on success return `{question, answer, citations}` with `citations` being the retrieved chunks' metadata (so each citation names the exact `control_id`/`framework`/`title` it's grounded in); every exchange (verified or not) is persisted to `ChatHistoryStore` so history reflects exactly what the admin saw.

**Judgment call: verify-fails fallback.** When `verify()` returns `False` (or when retrieval returned zero chunks, treated the same as an unverifiable answer), the endpoint returns a fixed fallback string (`UNVERIFIED_FALLBACK` in `chat.py`: "I'm unable to verify an answer to that question from this device's recorded findings and control text.") with an **empty citations list**, and persists that fallback exchange to history rather than the discarded draft -- the unverified draft is never returned to the caller and never written to disk, anywhere. This is stricter than "show it but flag it," on the reasoning that the spec explicitly frames `verify` as a trust gate ("the chat doesn't casually assert something the facts don't support"), not an advisory annotation.

**Judgment call: citation format.** Citations are the raw metadata dict per retrieved chunk (`control_id`, `framework`, `title`, `status`) rather than a separate citation-formatting layer, since the metadata already *is* what's needed to look the finding back up in the device's own report -- no extra indirection added.

**Dependency**: `chromadb` added to `backend/requirements.txt` (this repo manages backend deps via `requirements.txt` + a bare venv, not a `uv`-managed `[project]` table -- `pyproject.toml` has no `[project]` section, so `uv add` isn't available here; installed instead via `uv pip install chromadb` into `.venv`, matching how the rest of `requirements.txt` was evidently installed). Added a scoped `[[tool.mypy.overrides]]` for `chromadb.*` (`ignore_missing_imports`) since chromadb ships no type stubs; nothing else needed the leniency.

**Smoke tests**: `backend/tests/test_llm_smoke.py` exercises the real `OllamaLlmClient` against `http://localhost:11434`. Marked `@pytest.mark.llm_smoke` and excluded from the default run via `addopts = "-m \"not llm_smoke\""` in `pyproject.toml` (kept out of the main suite's fast feedback loop, per spec) -- *and* each test independently checks Ollama reachability at runtime and calls `pytest.skip(...)` if it's not up, so even a direct `pytest -m llm_smoke` invocation on a machine with no Ollama running skips cleanly instead of failing or hanging. Verified both paths: default `uv run pytest -q` deselects them (105 pre-existing + 14 new = 119 passed, 3 deselected); `uv run pytest -m llm_smoke` shows `3 skipped`.

**Wiring**: `main.py`'s `create_app` gained one new optional parameter, `llm_client: LlmClient | None = None`, defaulting to `OllamaLlmClient()` -- every existing caller/test is unaffected. `uv run mypy app` is strict-clean across all 18 source files including the four new ones.
